# Problem Structuring

仅在需要深入理解赛题、建立数学抽象、进行 Decomposition 或调整 Living Task Graph 时读取本文。

## 1. Grounding

先理解具体问题，再选择方法。

重点确认：

- 题目实际要求回答什么；
- 最终需要提交什么；
- 提供了哪些数据、附件和领域事实；
- 有哪些明确约束；
- 单位、尺度和时间范围是什么；
- 评价要求或目标函数是什么；
- 哪些信息缺失、模糊或相互矛盾。

避免只根据题目中的关键词直接套用熟悉模型。

如果缺失的信息、用户意图或题目歧义会实质影响建模方向，并且无法从赛题材料中恢复，可以向用户提问。

## 2. Abstraction

把具体赛题映射成更清楚的数学结构。

可能涉及：

- prediction；
- optimization；
- classification；
- evaluation；
- simulation；
- mechanism modeling；
- graph / network；
- time series；
- uncertainty analysis；
- multi-objective decision；
- 其他适合当前问题的结构。

这些类别只用于帮助思考。一道赛题可以同时包含多种数学结构。

不要为了匹配某个熟悉方法而强行改变问题定义。

## 3. Decomposition

将全局问题拆成适合局部处理的 Task。

一个好的 Task 通常具有：

- 清楚的局部目标；
- 可以由 Solver 在干净可控的上下文中独立理解的边界；
- 可解释的上下游依赖；
- 对全局求解有实际价值的输出。

优先让 Task 表达认知或计算上的自然边界。

避免：

- 为了增加子智能体数量而拆分；
- 把一个高度耦合的问题强行切碎；
- 把纯机械动作伪装成独立 Task；
- 产生大量无法形成有效语义交接的小 Task。

## 4. Living Task Graph

`task-graph.md` 表达主会话当前对问题结构、Task 与依赖关系的理解。

它是动态计划，可以随着事实变化持续修改。

常见修改包括：

- 新增 Task；
- 删除已经失去价值的 Task；
- 拆分过大的 Task；
- 合并高度耦合的 Task；
- 修改依赖关系；
- 增加验证、敏感性分析或替代方案；
- 因下游矛盾重新打开上游问题；
- 因新的研究结果改变方法路线。

Task Graph 使用人类可读 Markdown。

不要求固定字段。不要让 Runtime 通过 schema 或 enum 决定语义状态。

## 5. 什么时候重新规划

出现以下情况时，优先重新检查 Task Graph：

- 新证据推翻了关键假设；
- 某个 Task 的结果与全局模型冲突；
- 多个 Task 对同一变量、定义或单位理解不一致；
- 当前方法无法达到题目要求；
- 研究发现更合适的方法路线；
- 继续求解当前 Task 的边际价值已经很低；
- 报告阶段时发现问题覆盖存在缺口。

重新规划可以影响任何层级。不要把已经完成的 Task 视为永久关闭。

## 6. 主会话的判断重点

在问题结构化阶段，主会话最重要的任务是保持问题定义和全局逻辑稳定。

持续检查当前数学抽象是否仍对应原题要求，以及 Task 划分和依赖关系是否保留了全局问题的真实逻辑。
